## Détail des constats hauts et moyens

### 1. Des saisies de l'application peuvent entrer dans l'échantillon humain et le kappa, sans test

Six appelants filtrent en ligne `estDuRun(r) && r.statut_reponse === "obtenue"` : le jeu d'or, le
contrôle de la notation, la notation simulée, la lecture du run, le go/no-go et l'écran de notation
humaine. Aucune fonction ne porte cette population. `chaine.ts:756` tire l'échantillon de 10 % sur la
liste que l'appelant lui passe. Or une saisie de l'application est de contexte `run`, de statut
`obtenue` et de canal `application` : elle passe le filtre. Le §5 (« Tailles ») et
`pipeline/run/reponses.ts:reponsesObtenues` ne comptent que le canal API, et les métriques
secondaires refusent déjà tout autre canal (`exigerCanalApi`).

Le scénario : un run mensuel désigné pour l'application. Des saisies exploratoires (QR8) entrent
dans l'échantillon humain, puis dans l'accord humains et le kappa de l'échantillon publiés. Aucun
message ne le signale. Le run pilote n'est pas touché, car il n'a pas d'application désignée, et
aucun test ne construit ce cas.

Le §7 dit « parmi les réponses obtenues » sans préciser le canal : c'est un trou du protocole.
Option recommandée : le canal API seul, par cohérence avec le §5. Ensuite, une fonction unique
`analysis/population-notation.ts` (ou voisine), lue par les six appelants, avec le test du run
désigné.

La gravité haute impose de corriger, ou d'inscrire le constat à `docs/DETTE.md` si l'amendement
tarde. Il doit être réglé avant le premier run mensuel avec application.

### 2. Deux commandes qui réécrivent `run.json` en même temps se marchent dessus

Sept écrivains font la même chose : lire `run.json`, fusionner leurs champs, écrire un temporaire
`run.json.<suffixe>` ouvert en `wx`, puis le renommer sur la cible. Le suffixe diffère d'une commande
à l'autre. Le temporaire exclusif empêche donc deux `pnpm kappa:jeu-or` simultanés, mais pas un
`pnpm kappa:jeu-or` lancé pendant l'étape 3 bis de la chaîne : le dernier renommage efface
`contrefactuel_outils` ou les kappas du jeu d'or. Une relance réinscrit le champ perdu, mais un
`pnpm analyze` lancé entre-temps fige dans son empreinte un `run.json` amputé.

C'est la famille du constat 1 du 2026-11-05, corrigé pour `metriques.json`. Correction recommandée :
garder le contenu lu et le relire avant le renommage, puis refuser par une erreur nommée
(`RunModifieEntreTemps`) s'il a changé. La fenêtre restante est de quelques microsecondes. Test :
simuler l'écriture concurrente entre la lecture et le renommage.

### 3. `pnpm test` et deux scripts ne tournent pas sous Windows

Le correctif du constat 5 du 2026-11-05 voulait un `pnpm test` qui passe sur tout clone propre. Sous
Windows, deux choses le cassent :
- le `globalSetup` lance `execFileSync("pnpm", …)` sans shell. Node refuse un `.cmd` sans shell
  (`EINVAL` depuis Node 18.20.2 et 20.12.2), et sur la machine de l'auteur `pnpm` n'existe que via
  `corepack pnpm` (`ENOENT`) ;
- même lancé, `build:site` échoue : pnpm exécute les scripts par `cmd.exe`, qui ne connaît pas la
  forme `VAR=1 commande`. C'est reproduit : « 'ASTRO_TELEMETRY_DISABLED' n'est pas reconnu… ».
  `pnpm dev`, que CLAUDE.md recommande pour tout essai, a la même forme.

La CI Linux est verte, d'où l'absence de signal. Correction recommandée :
- dans le setup, lancer `process.execPath` sur `process.env.npm_execpath` ;
- pour les deux scripts, soit `shell-emulator=true` dans un `.npmrc` (réglage de pnpm, aucune
  dépendance), soit la variable posée par l'outil lui-même.

Ce constat rejoint le lot de portabilité Windows proposé et non décidé (mémoire d'environnement de
l'auteur, 49 échecs Vitest propres à Windows).

### 4. La règle des décisions vérifiantes est écrite trois fois

`versions-promues.ts` (nouveau, #380) déclare `RETENUES = {accepter, corriger}`, puis appelle
`validationsConcordantesMemeVersion`, qui refiltre. `invariants.ts:243` écrit la même condition en
ligne, et `kappa.ts:categorieDe` la troisième fois. Si une décision vérifiante s'ajoute à `DECISIONS`,
le contrôle a posteriori de `pnpm promote` et le kappa de validation ne retiennent plus les mêmes
décisions, et aucun test ne casse. Correction : une constante `DECISIONS_VERIFIANTES` à côté de
`DECISIONS`, lue aux trois endroits, et un seul filtre dans `versions-promues.ts`.

### 5. La garde « simulé seulement » vit dans les commandes, pas dans les fonctions qui écrivent

`pipeline/run/simulation.ts` se dit le seul lieu de la règle D92 (c). Pourtant ce sont
`outils/run-dry.ts` et `outils/interrogation-stocker.ts` qui appellent `exigerGelSimule`, chacune
sous un `existsSync(run.json)` recopié. `lancerRunGeleSimule` et `stockerRunGeleSimule` acceptent un
gel réel : un nouvel appelant (une commande, une chaîne de bout en bout) qui oublie la garde
inscrirait `statut: en_cours` et des réponses simulées dans un run réel gelé hors de `runs/`.
Correction : la garde dans les deux fonctions, juste après `lireRunGele`, qui refuse déjà un
`run.json` absent ; les deux blocs des commandes disparaissent.

### 6. Le plan du site interdit ce que le site fait déjà, et rien ne borne ses imports

`docs/PLAN-PAGE-PEDAGOGIQUE.md:109` est le cadre du site de résultats qu'on s'apprête à écrire. Il
dit « aucun import depuis `pipeline/` ni `analysis/` ». Or `site/src/lib/parametres.ts` importe
`analysis/bootstrap.ts`, `parametres-protocole.ts` et `seuils.ts` : c'est le correctif voulu du
constat 4 du 2026-11-05, et la leçon de #333 explique pourquoi ces constantes vivent dans
`analysis/`. Le site de résultats lira `runs/` et aura besoin des types d'`analysis/`.

Un agent qui suit le plan à la lettre défera le correctif ; un agent qui suit le code importera
peut-être `pipeline/` ou `validation/`, et rien ne l'arrêtera. Correction recommandée : réécrire la
phrase du plan (« constantes, types et fonctions pures d'`analysis/` seulement ; jamais `pipeline/`,
`validation/`, `staging/` »). La tenir ensuite par une règle `no-restricted-imports` sur
`site/**/*.ts`, calquée sur celle d'`analysis/**`. Les fichiers `.astro`, que le lint ne lit pas,
restent couverts par la garde réseau.
