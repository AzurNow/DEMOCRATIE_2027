## Détail des constats hauts et moyens

### 1. Le renvoi à la réextraction reste « à trancher » dans les trois cas que la 0.27 a tranchés : un seul « rejeter » sous le motif, rejet arbitré, item O à deux sources.

*protocole → code, §4.113, §4.114, §4.115, `validation/domaine/renvoi-reextraction.ts:examiner, examinerSources ; schema/decision-arbitrage.schema.json`.*

Le protocole dit (0.27, D62 #233 (1)) : le renvoi a lieu dès qu'une décision de rejet qui fonde le rejet porte le motif, y compris un seul des deux « rejeter », la décision de l'arbitre porte le motif comme celle d'un annotateur, et les deux sources d'un item O sont renvoyées. Le code (#233, antérieur à la 0.27) ne renvoie que sur deux « rejeter » concordants qui portent tous deux le motif et une seule source ; les trois autres cas sont imprimés « à trancher » (motifs_discordants, rejet_arbitre, plusieurs_sources), et decision-arbitrage.schema.json n'a aucun champ de motif de rejet. Trois tests de tests/renvoi-reextraction.test.ts verrouillent cette lecture. Ce que ça change : renvoi-texte-errone.ts ne part que des renvois tranchés, donc les autres items validés sur un texte faux restent vérifiés et entrent au tirage ; c'est visible de l'auteur dans la sortie de pnpm promote, pas du lecteur.

**Proposition** : corriger le code : dans examiner, renvoyer dès qu'une décision de rejet porte le motif ; ajouter motif_rejet facultatif (même énumération) à decision-arbitrage.schema.json et à pnpm arbitrer, lu comme une décision de rejet ; dans examinerSources, renvoyer chaque source distincte ; réécrire les trois tests « à trancher » en tests de renvoi.

### 2. Un item F est vérifié par deux « accepter » même si les annotateurs répondent non à la question de fictivité.

*protocole → code, §4.126, `validation/domaine/promotion.ts:verifier`.*

Le protocole dit (0.28, D70 (9)) : « Il n'est vérifié que si deux annotateurs confirment, par la grille de son type, que la mesure est absente des corpus balayés. » Le code exige, pour un item A seulement, que les deux décisions répondent oui à confirmation_absence (absenceConfirmee) ; pour un item F, controlerSpecifiques exige une réponse booléenne à fictivite_verifiee, sans en lire la valeur. Ce que ça change : une mesure faussement fictive, dont un annotateur a pourtant signalé une occurrence, entre au tirage ; toute réponse correcte d'un outil sur elle compte comme fabrication.

**Proposition** : corriger le code : dans verifier, envoyer en arbitrage (motif nommé, par exemple confirmation_fictivite_manquante) un item F dont les deux décisions ne répondent pas oui à fictivite_verifiee, sur le modèle de absenceConfirmee ; test dans tests/promotion.test.ts.

### 3. Deux items en vigueur aux positions incompatibles arrêtent tout le gel au lieu d'être exclus du tirage et comptés à part.

*protocole → code, §5.60, §5.61, `pipeline/questions/reponse-attendue.ts:PositionsContradictoires ; pipeline/questions/tirabilite.ts:motifDExclusion`.*

Le protocole dit (0.27, D67) : les deux items sont exclus du tirage et comptés à part, la mesure n'engendre aucune question d'attribution tant qu'ils le sont, et l'auteur les conteste dès le gel. Le code lève PositionsContradictoires dans reponseAttendue d'une Q-ATT ; motifDExclusion la laisse remonter (« tout autre refus remonte et arrête le tirage »), donc aucun run ne se gèle. Aucun motif d'exclusion ne nomme ce cas dans MOTIFS_EXCLUSION, et rien ne liste les items à contester. Ce que ça change : aucun chiffre faux, mais un arrêt ; l'auteur doit contester les items à la main avant le gel, et ils sont alors comptés comme contestés, pas sous le motif que le protocole publie.

**Proposition** : corriger le code : un motif d'exclusion nommé (par exemple positions_incompatibles) appliqué aux questions des deux items et à la Q-ATT de la mesure, compté dans tirage.exclusions, et la liste des items à contester imprimée par pnpm geler ; tests dans tests/questions/tirabilite-au-gel.test.ts et tests/gel/geler.test.ts.

### 4. Le nombre de réponses obtenues n'est jamais inscrit dans run.json, et sa restriction au canal API n'est gardée par aucun test.

*protocole → code, §5.64, §5.65, `pipeline/run/reponses.ts:inscrireReponsesObtenues ; pipeline/notation/chaine.ts`.*

Le protocole dit (0.27) : le nombre de réponses obtenues est inscrit au début de la notation, et ces nombres ne portent que sur le canal API. Le code compte (reponsesObtenues, refus compris, canal api) et sait inscrire (inscrireReponsesObtenues, testé), mais aucune commande ne l'appelle : la chaîne de notation n'écrit pas run.json#/reponses/obtenues. Le filtre du canal (reponsesApiDuRun) n'est exercé par aucun test du compte. Ce que ça change : un run publié n'a que ses réponses prévues ; le nombre obtenu manque, visiblement, au lieu d'être faux.

**Proposition** : corriger le code : appeler reponsesObtenues puis inscrireReponsesObtenues en tête de la chaîne de notation, après la garde d'attente de l'opérateur, avec un test de chaîne ; ajouter à tests/run/reponses.test.ts un cas où une saisie du canal application n'est pas comptée.

### 5. La fenêtre d'un run supplémentaire est refusée si elle ne s'ouvre pas un mardi, alors que la 0.27 l'ouvre à 6 h le premier jour qui suit son gel.

*protocole → code, §6.34, `pipeline/interrogation/fenetre.ts:ouvrirFenetre`.*

Le protocole dit : « un run supplémentaire ouvre sa fenêtre à 6 h, heure de Paris, le premier jour qui suit son gel » (§6, 0.27, D67). Le code fait : ouvrirFenetre, appelée par le gel (assemblage.ts), la reprise de l'interrogation (run-gele.ts) et la checklist du go/no-go, refuse tout début qui n'est pas un mardi à 06:00 heure de Paris, sans lire type_run ; tests/interrogation/fenetre.test.ts « refuse %s » garde ce refus pour un lundi. Ce que ça change : un run supplementaire_debat ou supplementaire_liste_officielle gelé un autre jour que le lundi ne peut ouvrir sa fenêtre que le mardi suivant, jusqu'à six jours plus tard, ce qui rend l'engagement des 72 heures du §6 intenable ; aucun chiffre faux, mais un run décalé sans que rien ne le signale.

Tests : un supplémentaire gelé un samedi s'ouvre le dimanche à 6 h ; un supplémentaire ouvert un mardi qui n'est pas le lendemain du gel est refusé ; changement d'heure.

### 11. Le code exige un extrait justificatif d'une note non exacte sur une réponse au texte vide, que l'annexe C exempte depuis la 0.27.

*protocole → code, C.04, `schema/notation.schema.json:allOf[13] ; pipeline/notation/extrait.ts:controlerExtrait ; pipeline/notation/notation-humaine.ts:construireNotationHumaine`.*

### 12. Un couple comparé dont la différence de H3 ou la tendance de H5 n'est pas définie est publié « sans objet », règle que le §2 n'écrit que pour H2.

*code → protocole, §2.20, §2.24, `analysis/hypotheses.ts:coupleCompareH3 (paire_absente, exactitude_indefinie) ; analysis/hypotheses.ts:coupleCompareH5 (tendance_indefinie)`.*

Le protocole dit, pour H3 : « Un couple qui n'est pas comparé, c'est-à-dire sans objet ou marqué « run incomplet » (section 8), est publié « sans objet » » ; pour H5 : « Un couple outil × mode qui sort de la comparaison de tendance (section 8) est publié « sans objet » », la section 8 n'en faisant sortir que le couple marqué run incomplet. Seule H2 a reçu en 0.26 (D61) la règle de la différence indéfinie. Le code rend aussi « sans objet » un couple comparé sans aucune question F ou O dans un registre (paire_absente) ou dont un registre n'a aucune réponse classée (exactitude_indefinie) pour H3, et un couple présent à un seul run ou sans réponse classée commune (tendance_indefinie) pour H5. Ce choix décide entre « sans objet » et « non confirmée » d'un couple, et pour H5 s'il compte parmi les couples comparés de l'outil : un verdict publié change, en cas limite.

**Proposition** : réviser le protocole. Au §2, après la règle de H3 : « Un couple comparé dont la différence est indéfinie, parce qu'aucune question sur un item F ou O n'y forme de paire ou que l'un des deux registres n'a aucune réponse classée sur les questions appariées, est publié « sans objet » pour H3. » Après la règle de H5 : « Un couple dont la tendance est indéfinie, parce qu'il n'est présent qu'à l'un des deux runs ou qu'il n'a aucune réponse classée sur les questions communes, est publié « sans objet » pour H5 et ne compte pas parmi les couples comparés de l'outil. »

### 13. L'analyse avec premier run s'arrête quand un outil du premier run n'est plus au périmètre du dernier, cas que le §2 ne règle pas.

*code → protocole, §2.24, `analysis/hypotheses.ts:verifierOutilsDeLaTendance (TendanceIncoherente)`.*

Le protocole dit : « H5 : l'exactitude de chaque outil est plus élevée au dernier run qu'au premier », et la liste des outils « ne bouge qu'en cas de disparition d'un outil ou de sortie d'un nouvel outil » (§3). Il ne dit pas ce que devient H5 pour un outil présent au premier run et sorti avant le dernier. tendance.ts:tendanceParOutilEtMode garde une ligne pour tout couple rencontré dans l'un des deux runs, et decisionH5 lève TendanceIncoherente sur une ligne d'un outil que le dernier run ne déclare pas : pnpm analyze --premier échoue. Le code le signale lui-même en commentaire. Aucun nombre faux, mais H5 devient incalculable dès la disparition d'un outil, cas que le §3 prévoit.

**Proposition** : réviser le protocole. Au §2, après la règle de H5 : « H5 est décidée pour les seuls outils inclus au dernier run ; un outil sorti du périmètre depuis le premier run n'a pas de verdict H5, et ses couples sont rapportés avec la tendance sous ce motif. » Puis remplacer le refus par ce rapport, avec son test.

### 14. Un nom ambigu entre deux candidats éliminés est écarté sans renvoi humain, alors que le §3 envoie chez un humain tout nom qui peut désigner un éliminé « et un autre candidat ».

*code → protocole, §3.37, `pipeline/notation/note-attribution.ts:noterAttribution`.*

Le protocole dit : « un nom qui peut désigner un candidat éliminé et un autre candidat est un nom ambigu : la réponse qui le cite est notée par un humain, exacte ou inexacte (annexe B) » (§3, 0.29, D71 (3)), et au §7 que le nom d'un éliminé « est écarté des candidats cités avant l'application de la règle ». Le code lit « un autre candidat » comme un candidat non éliminé : un nom ambigu dont tous les candidats possibles sont éliminés est écarté comme eux (test « nom ambigu dont tous les candidats possibles sont éliminés : écarté comme eux »), un nom ambigu entre un éliminé et un qualifié part chez un humain. La lecture du code est cohérente avec le §7, mais la lettre du §3 couvre aussi deux éliminés homonymes. Le classement d'une réponse (note automatique contre note humaine) en dépend, en cas limite.

**Proposition** : réviser le protocole : remplacer au §3 « un nom qui peut désigner un candidat éliminé et un autre candidat est un nom ambigu » par « un nom qui peut désigner un candidat éliminé et un candidat qualifié est un nom ambigu », et ajouter : « un nom qui ne peut désigner que des candidats éliminés est écarté comme eux ».

### 15. L'écart juge-éditeur sort de la moyenne un autre outil dont l'écart n'est pas défini, et écarte les rééchantillons où un écart retenu cesse de l'être, ce que le §7 n'écrit pas.

**Proposition** : réviser le protocole, au §7 après « …avec le composant `<juge>:propre-editeur`. » : « Un autre outil sur lequel l'un des deux juges ne classe aucune réponse n'a pas d'écart : il sort de la moyenne et il est nommé. ### 17. Une citation rejetée par le test verbatim ne compte pas comme proposition de position pour la promotion d'un item A, règle que le protocole n'écrit pas.

*code → protocole, —, `validation/domaine/absence.ts:refusPromotionAbsence (D62 #233 (4))`.*

## Détail des constats bas

- **18.** Le code exige le sondage archivé et la notice déclarée, sans en confronter le contenu ; même situation que le constat n° 9 de la mise à jour du 2026-11-01 (§3.03, §3.06, §3.07), accepté. *Proposition* : accepter : la case 1 de l'annexe F est déclarée par l'auteur au contreseing, sur les pages archivées publiées.
- **19.** Aucun critère du go/no-go ne lit le nombre de candidats ni le régime : l'exigence est tenue par construction, sans garde. *Proposition* : accepter : la règle est l'absence d'adaptation, et le go/no-go ne publie aucun nombre.
- **20.** La 0.28 (D70 (9)) écrit qu'un item F est rédigé par l'auteur et que son auteur est publié avec lui ; ni le schéma de l'item ni celui de la mesure ne le portent, et la feuille de route n'inscrit aucun lot de création des items F. *Proposition* : corriger le code : un champ redige_par exigé sur un item F (schéma, exemple invalide), et un lot inscrit à la feuille de route pour la création des items F.
- **21.** Le protocole dit (0.27) que les trois formulations sont relues « avec l'item principal de la question ». L'écran montre candidat, mesure, position demandée et les trois textes, ni le type, ni la citation, ni la quantification de l'item. *Proposition* : corriger le code : ajouter à la vue de relecture l'identifiant, le type et le contenu notant de l'item principal, avec un test de la route.
- **22.** La 0.27 étend la vérification aux corpus T1 et T2 et aux items T3 ; verification_fictivite ne porte que les candidats balayés et sa description parle encore des seuls corpus T1. *Proposition* : corriger le code : mettre la description à jour et ajouter à verification_fictivite les niveaux balayés (T1, T2, items T3), exigés tous trois, avec un exemple invalide.
- **23.** La 0.27 écrit que le changement de quota est publié avec le run, avec sa raison ; le quota est publié, mais aucun champ ne porte la raison ni ne compare au run précédent. *Proposition* : corriger le code : clé facultative raison_changement_quota dans config/perimetre.yaml, exigée au gel quand un quota diffère de celui du run précédent inscrit, recopiée dans tirage.parametres.
- **24.** Le protocole dit : « Le troisième humain n'est jamais l'auteur, qui connaît la table des alias d'outils » (§7, 0.27, D67). Le code fait : il refuse un arbitre qui est l'un des deux premiers annotateurs, mais ne connaît pas le pseudonyme de l'auteur ; ANNOTATEUR_ID est libre. Ce que ça change : une note retenue de l'échantillon pourrait venir d'un humain non aveugle à l'outil sans que rien ne le signale ; processus, aucun chiffre changé tant que la consigne est suivie. *Proposition* : corriger le code : l'auteur déclare son pseudonyme d'annotateur dans la configuration du gel (champ à ajouter, saisi par lui), et la notation humaine refuse une notation d'arbitrage (arbitrage_echantillon_10, arbitrage_comparateur, troisième humain du jeu d'or) portant ce pseudonyme ; test associé.
- **25.** Le protocole dit : « Tous les taux, ceux des métriques secondaires compris, sur chacune de leurs strates, sont accompagnés d'un intervalle de confiance à 95 % ». Le code publie test.exactitude_outil (taux sur les seules réponses classées aux questions nommant un candidat comparé) sans intervalle. C'est un deuxième chiffre d'exactitude de l'outil, différent de l'exactitude de la strate global (Q-ATT et candidats sous le seuil exclus), qu'un lecteur pourrait confondre avec elle. Aucun nombre faux, mais un taux publié hors de la règle. *Proposition* : corriger le code : publier cette valeur comme la statistique de référence du test (champ renommé, hors du type taux publié), ce qui ne demande aucune révision ; à défaut, lui donner un intervalle nommé, dont la clé devrait alors être écrite au §8.
- **26.** Le protocole dit : « la part des réponses qui citent une page du projet est publiée par couple, en diagnostic (section 11) ». Aucun module d'analysis/ ne la calcule, et aucune donnée (périmètre, run.json) ne déclare les domaines du projet ; le site n'existe pas encore, donc ses adresses ne sont pas connues. Ce n'est pas une métrique, mais le code devra fixer le domaine reconnu et le dénominateur, qu'aucune phrase n'écrit. Hors du périmètre annoncé du sous-lot B. *Proposition* : réviser le protocole, puis coder : « Une réponse cite une page du projet quand l'un des liens qu'elle cite a pour hôte l'un des domaines du projet, ou l'un de leurs sous-domaines, déclarés au périmètre du run ; la part est le nombre de ces réponses sur les réponses obtenues du couple, publiée sans qualificatif, avec son intervalle. »
- **27.** Le protocole dit : « la version du protocole et son empreinte, ainsi que la version du code et des données utilisée, sont inscrites en tête de chaque rapport. » pnpm geler écrit versions.protocole_sha256 (testé par tests/gel/geler.test.ts), mais run.schema.json ne le requiert pas, alors qu'il requiert protocole, code_commit et donnees_commit. Un run écrit autrement que par le gel pourrait être publié sans empreinte. C'est une exigence de donnée gardée par le code mais pas par le schéma. *Proposition* : corriger le code : ajouter protocole_sha256 à versions.required (ou à la règle des runs publiés et invalides), avec un exemple invalide dans schema/exemples/run/.
- **28.** Le §9 dit depuis la 0.27 : « Une notation publiée se corrige par une notation humaine nouvelle […] C'est aussi la règle de tout erratum. » pipeline/run/statut.ts et le $comment de run.schema.json allOf[1] disent : « un défaut découvert après publication serait un erratum, que le protocole ne prévoit pas ». La règle (un run publié ne porte jamais d'invalidation) reste juste ; seule la justification est périmée. La règle de correction elle-même n'a pas d'outil (§9.26, a-implementer). *Proposition* : corriger le code : remplacer les deux commentaires par un renvoi à la règle d'erratum du §9 (correction par notation humaine nouvelle, chiffre republié à côté de l'ancien).
- **29.** Le prompt de juge dit déjà qu'un « non » sans correction reste exact ; seul le nom de la nature est périmé. Le renommer toucherait le schéma, la charge du juge et prompts/judge-*, zone d'arrêt. *Proposition* : accepter : nom interne sans effet sur une note, le prompt porte la règle de la 0.27 ; à reprendre avec la prochaine version de la charge du juge.
- **30.** Le protocole dit que le motif renvoie la source à la réextraction ; pnpm extraire ne relance pas une source journalisée et l'extracteur épinglé rendrait le même texte. Question connue et laissée sans lecture (D62 #233 (2), D70 (14) ; docs/DETTE.md). *Proposition* : réviser le protocole (décision de l'auteur). Texte proposé, au §4 après « renvoie la source à la réextraction » : « La source renvoyée est réextraite par une autre version de l'extracteur de texte ou par une transcription manuelle publiée, qui produit un nouveau texte canonique ; tant qu'elle ne l'est pas, aucun item n'est validé sur cette source. »
- **31.** Le §5 (0.27) dit que les 20 % de questions neuves « permettent une analyse exploratoire de la part de la mémorisation dans l'amélioration » ; le §8 ne la définit pas et aucun code ne la calcule. Le code ne peut pas l'implémenter sans trancher une méthode. *Proposition* : réviser le protocole (décision de l'auteur) : soit définir au §8 l'analyse (par exemple, par outil et par mode, différence d'exactitude entre questions reprises et neuves du même run, intervalle bootstrap en grappes, exploratoire), soit écrire au §5 qu'elle n'est pas calculée en version 1.0.
- **32.** Le protocole dit : « cinq par candidat interrogé » et « Les cinq questions d'un candidat sont réparties entre ses gabarits » (§6). Le code fait : les Q-ATT, qui ne nomment aucun candidat, sont exclues (test « les questions d'attribution, qui ne nomment aucun candidat, n'entrent pas au sous-échantillon »). Ce que ça change : l'écart API / application exploratoire ne porte jamais sur une question d'attribution. *Proposition* : accepter : c'est la seule lecture de « cinq par candidat interrogé » pour une question qui ne nomme personne, et l'écart est exploratoire ; à écrire au besoin d'un mot à la prochaine révision.
- **33.** Le protocole dit : « les noms permutés sont le libellé et l'éditeur de chaque outil déclarés au périmètre, selon un dérangement des outils du run » (§7). Il ne dit pas quoi faire quand deux outils ont le même éditeur. Le code fait : tirerDerangementOutils lève FormesOutilsAmbigues (tests « deux outils du même éditeur : refus nommé, jamais départagé », « libellé égal à l'éditeur d'un même outil : refus nommé »). Ce que ça change : un périmètre avec deux produits d'un même éditeur rend le test impossible à jouer ; déjà relevé, sans lecture écrite (D62 #235 (4), D70 (14)). Le test n'étant pas encore branché, aucun run n'est touché aujourd'hui. *Proposition* : réviser le protocole (trou à trancher par l'auteur). Texte de l'option qui garde le code : « Quand deux outils du périmètre ont le même éditeur, ou qu'un libellé est aussi un éditeur, le remplacement serait ambigu : le contrefactuel d'outil n'est pas défini pour ce run, et il est publié absent, avec ce motif. »
- **34.** Le protocole dit : « Une paire dont un échantillon n'est pas obtenu, est « indéterminé » ou « non classé, référence incomplète » est écartée, et ces paires sont comptées à part, par motif ». Le code distingue deux motifs pour « non obtenu » (aucun, un seul) et, quand une paire relève de deux motifs, retient le premier de MOTIFS_PAIRE_ECARTEE : une paire non classée et indéterminée est comptée non_classee. Les comptes publiés par motif en dépendent ; l'accord lui-même n'en dépend pas. *Proposition* : réviser le protocole, au §8 après « par motif » : « Une paire écartée l'est sous un seul motif, le premier qui s'applique dans cet ordre : aucun échantillon obtenu, un seul échantillon obtenu, un échantillon « non classé, référence incomplète », un échantillon « indéterminé ». »
- **35.** Le protocole dit seulement que le recalcul (b) mis à jour « est publié dans un fichier daté, à côté de lui ». Le code refuse un second fichier pour le même jour : une deuxième contestation postérieure reçue le jour d'un recalcul n'est publiée que le lendemain. Aucun nombre ne change ; seul le délai de publication. *Proposition* : accepter : sans effet sur un nombre publié ; le recalcul se refait le lendemain, et le refus est nommé.
- **36.** Le code est cohérent avec la règle du gel (`decisionAvantGel`, `<=`) : une contestation reçue à l'instant du gel compte comme antérieure. Le texte du recalcul (b) dit « contesté à un run ultérieur » sans borne. Ne change un nombre que pour une contestation reçue à la seconde du gel. *Proposition* : réviser le protocole. Au §8, après la définition du recalcul (b) : « Une contestation est postérieure à un run quand elle est reçue strictement après l'instant de gel de ce run. »
- **37.** Le protocole dit (0.30) : « Il y a égalité des voix quand aucune décision ne réunit la majorité absolue des membres votants, les membres déportés ne votant pas et étant publiés avec la délibération. » L'annexe E rattache les déportés au seul cas d'égalité. Le code les publie pour une délibération sans majorité (deliberations_sans_majorite[].deportes, obligatoire) ; decision_panel n'a ni votes ni déportés, de sorte que la majorité absolue d'une décision enregistrée par --decision n'est pas vérifiable. Aucun nombre publié ne change. *Proposition* : réviser le protocole (trou à trancher). Option recommandée, au §10 après « publiées avec les opinions dissidentes » : « Les membres déportés sont publiés avec toute délibération, décision à la majorité comprise. » Puis ajouter deportes, obligatoire et éventuellement vide, à decision_panel.
