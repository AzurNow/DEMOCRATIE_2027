## Détail des constats hauts et moyens

### 1. Un kappa de la paire de juges inférieur à 0,75 sur le jeu d'or ne fait pas publier les résultats avec la mention « provisoire ».

*protocole → code, §7.23, `pipeline/go-no-go/criteres-juges.ts`, `schema/run.schema.json:kappa_paire_juges`.*

**Le protocole dit** : « Seuil de publication : kappa de la paire ≥ 0,75 sur la catégorie primaire ;
en dessous, les résultats sont publiés avec la mention « provisoire » et les juges sont retravaillés »
(§7).
**Le code fait** : depuis D93 (#345), `pnpm kappa:jeu-or` écrit `kappa_paire_juges` (ou son motif) dans
`run.json` du pilote. Aucun code ne le compare à 0,75 : le go/no-go (`critereKappaJugesHumains`) ne lit
que le kappa de l'échantillon de 10 % du §12, et le schéma accepte un run `publie` dont la paire vaut
0,6. La passe précédente le laissait de côté parce que la paire n'était écrite par personne (D89 en
cours) ; elle l'est maintenant, et la règle de seuil manque.
**Ce que ça change** : la mention « provisoire » d'un run publié, donc la lecture de tous ses
chiffres. Un run dont les juges s'accordent mal avec les humains sur le jeu d'or, mais bien sur
l'échantillon de 10 %, sortirait sans la mention. Le kappa de la paire reste publié, donc visible.
**Proposition** : code à aligner. Un critère `kappa_paire_jeu_or` dans `pipeline/go-no-go/`
(`criteres-juges.ts`), lu dans `run.json#/kappa_paire_juges` : rouge sous 0,75 (fraction exacte 3/4,
comme `SEUIL_KAPPA_ECHANTILLON`), donc `publie_provisoire` avec ce code dans le motif ; et la garde du
schéma : `statut: publie` ⇒ `kappa_paire_juges` présent et ≥ 0,75. Tests : « kappa de la paire 0,74 :
publie_provisoire », « exactement 0,75 : vert », « paire indéfinie : rouge ». Le cas indéfini n'est pas
écrit au §7 ; la lecture recommandée est celle du §12, à écrire dans la même révision, au §7 après
« …jamais leur prompt, dont le changement est un amendement. » : « Un kappa de la paire indéfini ne
satisfait pas ce seuil, comme en section 12. »

### 2. Un couple comparé dont la différence de H3 ou la tendance de H5 n'est pas définie est publié « sans objet », règle que le §2 n'écrit que pour H2.

*code → protocole, §2.20, §2.24, `analysis/hypotheses.ts:coupleCompareH3, coupleCompareH5`.* Inchangé
depuis le [2026-11-06](2026-11-06.md) (n° 2), où le détail est donné.

**Proposition** : amendement requis. Au §2, après « Un couple qui n'est pas comparé, c'est-à-dire sans
objet ou marqué « run incomplet » (section 8), est publié « sans objet » pour H3. » : « Un couple comparé
dont la différence est indéfinie, parce qu'aucune question sur un item F ou O n'y forme de paire ou que
l'un des deux registres n'a aucune réponse classée sur les questions appariées, est publié « sans
objet » pour H3. » Après « Un couple outil × mode qui sort de la comparaison de tendance (section 8) est
publié « sans objet » pour H5. » : « Un couple dont la tendance est indéfinie, parce qu'il n'a aucune
réponse classée sur les questions communes aux deux runs, est publié « sans objet » pour H5 et ne compte
pas parmi les couples comparés de l'outil. »

### 4. Le kappa juge-humain n'est inscrit qu'au run pilote, et le protocole ne dit pas comment il passe dans les runs suivants, dont le schéma l'exige pour être publiés.

*code → protocole, §7.22, §7.68, `pipeline/notation/inscription-jeu-or.ts:inscrireJeuOr`.*

**Le protocole dit** : le jeu d'or est tiré « avant le premier run » d'un run pilote et « sert à mesurer
l'accord juge-humain (kappa) pour chaque juge et pour la paire » ; « Tout juge dont le modèle ou les
réglages changent […] est mesuré à nouveau sur le jeu d'or […] avant son premier run » (§7). Rien ne
dit comment cette mesure figure dans le `run.json` d'un run mensuel ou hebdomadaire.
**Le code fait** : `pnpm kappa:jeu-or` refuse tout run qui n'est pas le pilote
(`InscriptionJeuOrRefusee`, test « un run qui n'est pas le pilote ») ; or `run.schema.json` exige de
tout run `publie` ou `publie_provisoire` le kappa de chaque juge et de la paire, ou leur motif.
**Ce que ça change** : aucun nombre faux ; aucun run autre que le pilote ne peut aujourd'hui être
publié. C'est la question Q3 de D89, tranchée en D94.
**Proposition** : amendement requis, puis code (recopie avec contrôle d'identité du juge, modèle et
réglages inscrits au gel). Texte de D94 (remplacement 5 de `TACHES-AUTEUR.md`), au §7 après « …porte
la mention de ce changement. » : « Le kappa juge-humain mesuré sur le jeu d'or est recopié dans chaque
run qui suit et que le juge note, depuis le jeu d'or de sa dernière mesure, tant que son modèle et ses
réglages inscrits au gel sont ceux de cette mesure ; la recopie est refusée pour un juge dont le modèle
ou les réglages diffèrent, qui doit d'abord être mesuré à nouveau. »

### 6. Un outil hors dérangement qui n'est pas un comparateur et partage l'éditeur d'un outil permuté bloque encore le contrefactuel d'outil, au lieu de le rendre absent.

*code → protocole, §7.84, `pipeline/notation/derangement-outils.ts:verifierOutils`.*

**Le protocole dit** : « Quand deux outils du dérangement ont le même éditeur, le test contrefactuel
d'outil est publié absent, avec ce motif, sans bloquer le run ; il en va de même quand un comparateur
du périmètre a le même éditeur qu'un outil du dérangement » (§7).
**Le code fait** : depuis D86 (#367), deux comparateurs du même éditeur qu'aucun outil permuté ne
porte ne bloquent plus (test « D86 : deux comparateurs non permutés du même éditeur : plus de refus,
dérangement identique à celui du périmètre sans ce doublon ») : cette moitié du n° 5 du 2026-11-06 est
réglée. Un assistant exclu (ou tout outil hors dérangement qui n'est pas un comparateur) qui partage
l'éditeur d'un outil permuté lève toujours `FormesOutilsAmbigues`, qui arrête la notation.
**Ce que ça change** : un run qui s'arrête au lieu de publier le test absent ; aucun nombre faux.
**Proposition** : amendement requis, puis code (étendre l'absence `comparateur_du_meme_editeur` à tout
outil du périmètre hors dérangement, ou un motif nouveau). Texte de D85 et D88 (remplacement 4), au
§7 : remplacer « il en va de même quand un comparateur du périmètre a le même éditeur qu'un outil du
dérangement. » par « il en va de même quand un outil du périmètre inscrit au gel, hors du dérangement,
comparateur ou non, inclus au run ou non, a le même éditeur qu'un outil du dérangement. »
