## Nouveaux constats

La numérotation suit celle du rapport de ce matin. Aucun constat ne contredit le protocole : ce sont
des écarts entre une règle écrite et ce que le code garde.

### Moyenne

**6. Rien ne vérifie que les deux juges sont de familles de modèle différentes.** §7.12.
- `pipeline/notation/chaine.ts:verifierJuges` exige deux juges, mais pas deux familles distinctes.
- Un run noté par deux juges d'un même éditeur passerait sans erreur.
- *Recommandé : corriger le code.* Il faut un refus nommé dans `verifierJuges`, avec son test.
  L'exclusion d'une famille d'Anthropic, si le protocole l'écrit, se contrôle au même endroit.

**7. L'accord juge-humain sur le jeu d'or n'est ni calculé ni défini pour « la paire ».**
§7.22 et §7.23.
- Le jeu d'or est tiré : `tirerJeuOr`, testé.
- Le seuil de 0,75 s'applique à chaque juge sur l'échantillon de 10 % du §12 (`critereKappaJugesHumains`).
- En revanche, aucun code ne calcule de kappa sur le jeu d'or, et le protocole ne dit pas ce qu'est le
  « kappa de la paire » : moyenne des deux juges, minimum, ou accord du verdict combiné.
- *Recommandé : réviser le protocole* pour définir ce kappa, puis l'implémenter dans `analysis/`. C'est
  un trou du protocole, à trancher par l'auteur.

### Basse

**5. Des règles portées par des prompts versionnés ne sont gardées par aucun test.**
- Exigences concernées :
  - §3.13 et §3.14 : exclusions du prompt d'extraction ;
  - §7.03, §7.04, §7.05, §7.15, D.01, D.05 : prompt de juge.
- Elles sont classées `sans-test`.
- Le prompt de juge porte le squelette de l'annexe D, mais aucun test ne le lit.
- *Recommandé : corriger le code.*
  - Ajouter un test structurel qui confronte `prompts/judge-1.0.0.md` au squelette de l'annexe D (les
    variables et l'ordre des blocs), sur le modèle de `tests/protocole-annexe-a.test.ts`. Le
    `prompts/judge-*` lui-même reste intouché.
  - Pour les définitions de classement (§7.03 à §7.05), *accepter* : seul l'accord juges-humains les
    mesure.

**8. L'accord entre les deux humains de l'échantillon n'est pas publié.** §7.30.
- L'aveugle est gardé.
- Le kappa humain-humain n'est écrit dans aucun fichier du run.
- *Recommandé : corriger le code* en le calculant dans `analysis/`, à côté du kappa juges-humains, et
  en le publiant dans `run.json#/go_no_go`.

**9. Les critères d'inclusion des outils et la correspondance à la liste officielle reposent
sur un relevé humain.** §3.03, §3.06, §3.07.
- Le code exige la preuve archivée.
- Il ne confronte pas son contenu.
- *Recommandé : accepter.* La case 1 de l'annexe F est déclarée par l'auteur au contreseing, et c'est
  le bon niveau de contrôle.
- À vérifier par l'auteur : le commentaire « jamais d'API » de `config/perimetre.yaml` (constat n° 52 du
  2026-09-29).

**10. Les paramètres d'échantillonnage effectifs sont enregistrés sans test ni exigence de
schéma.** §6.04.
- `executer.ts` écrit `parametres_effectifs`.
- `reponse.schema.json` ne l'exige pas (`metadonnees.required` n'a que les deux horodatages).
- Aucun test ne le vérifie.
- *Recommandé : corriger le code.* Le rendre obligatoire pour le canal api et ajouter un test.

## Ce que cette mise à jour ne dit pas

- Les exigences `testee` des lots interrogation et notation sont gardées sur l'adaptateur simulé et le
  juge simulé. Aucun adaptateur réel n'existe encore, et chacun devra porter les mêmes tests
  (§6.01, §6.03, §6.05, §8.10).
- Les 304 exigences déjà `testee` avant cette passe n'ont été revérifiées que par la passe automatisée
  de ce matin, pas relues à nouveau.
